what this actually is

Python ships.
Lean only has to catch one bug.

We are not rewriting the product in Lean. We are not golfing proofs. We are not spawning agents in CI yet. A script looks for a broken spec bullet, writes a tiny Lean proof of that bug, and asks Lean if the proof is real. If Lean says yes, the PR is denied. If it cannot prove a bug, the check stays green. Green is not “correct.”

Agents in CI?

Not today. GitHub Actions runs a Python script and Lean. No model gets launched. The folder has instructions for an agent we have not plugged in yet.

Theorem golf?

No. Golf is “make this proof shorter.” This is the other game: find one ugly counterexample and get Lean to stamp it.

Reimplement in Lean?

Only the toy model, not the product. A full Lean rewrite would be slow for real software. The product stays Python. Lean holds a small twin of it plus the spec.

What an agent would do later

Same loop a person would run. Read the bullets. Hunt for a case that breaks one. If Lean needs a helper fact, add a lemma. Stop when you have a stamped bug, or when you cannot find one.

Tap a real fixture

These are the actual bad files in the repo. The script already knows how to certify each one. An agent would be trying to invent this on a new PR.

The five steps

01 the spec
A few English bullets
“Do not mint money.” “Do not skip order states.” Written for humans first.
↓
02 a small search
Python tries a handful of inputs
Today that search is hardcoded. Later an agent would look harder.
↓
03 a certificate
One Lean file that says “this bug is real”
It can use helper facts. Those facts cannot mention the current code, because the deny path rewrites that code on purpose.
↓
04 Lean itself
The kernel checks the proof
Not an LLM. If this step says yes, the bug is actually a bug in the model.
↓
05 the PR
Deny, or stay green
Stay green means we failed to prove a bug. That is all it means.
